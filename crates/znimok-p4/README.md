# znimok-p4 — прототип P4: відтворення відео без копіювання кадрів (ZK-17)

Одноразовий вимірювальний код Фази 1. Що вціліє — переїде у відеокрейти Фази 8 (ZK-86, ZK-92).
Mac-частина (AVAssetReader → NV12-площини → wgpu Metal) — після P3 (ZK-16).

```
znimok-p4 selftest                            NV12→RGB у WGSL проти CPU-формули, штрих-код кадру
znimok-p4 info                                адаптер wgpu, підтримка NV12, D3D11 на тому самому LUID
znimok-p4 gen [-o f.mp4] [--size 3840x2160] [--fps 60] [--seconds 20] [--gop N] [--bpp 0.1]
znimok-p4 bench <f.mp4> [--mode zero|cpu|mflock|sw] [--paced] [--verify] [--frames N] [--lag N] [--lowlat]
znimok-p4 seek <f.mp4> [--mode …] [--count N] [--gop N] [--seed N] [--lowlat] [--rows]
znimok-p4 quality <f.mp4> [--every N]         PSNR декодованих кадрів проти кадрів генератора
```

Усі виміри й критерії однією командою: `python crates/znimok-p4/tools/p4_check.py [exe] [--dir ТЕКА] [--real запис.mp4]`
(потрібен зібраний `target/release/znimok-p4.exe`; тестові кліпи генерує сам прототип).

## Як це працює

1. **wgpu** — DX12 (Vulkan-драйвер Intel UHD 630 падає, як у P1/P2). З `ID3D12Device` беремо
   **LUID** адаптера й створюємо на ньому ж `ID3D11Device` (`EnumAdapterByLuid`) з `VIDEO_SUPPORT` і
   multithread-захистом. На гібридному ноутбуці декодер і рендер так гарантовано на одному GPU.
2. **Декодер** — MF Source Reader з `MF_SOURCE_READER_D3D_MANAGER` (`IMFDXGIDeviceManager` на цьому
   D3D11-пристрої) і `MF_READWRITE_ENABLE_HARDWARE_TRANSFORMS`, вихід NV12. Кадр — `IMFDXGIBuffer` →
   `ID3D11Texture2D` (зріз масиву текстур декодера) + індекс підресурсу.
3. **Міст** — пул із 4 NV12-текстур `SHARED | SHARED_NTHANDLE`, кожна відкрита в D3D12
   (`OpenSharedHandle`) і загорнута у wgpu: `hal::dx12::Device::texture_from_raw(…, TextureFormat::NV12, …)`
   → `create_texture_from_hal`. Площини — два view: `Plane0` як `R8Unorm`, `Plane1` як `Rg8Unorm`
   (фіча `TEXTURE_FORMAT_NV12`, DX12 її має). **`with_plane_slice` не знадобився.** Текстури декодера не
   shared, тож одна GPU-копія на кадр (`CopySubresourceRegion` з вікном 3840×2160 — декодер виділяє 2176
   рядків) неминуча.
4. **Синхронізація** — два спільні fence, обидва лише на GPU (CPU не чекає):
   copy (D3D11 `Signal` після копії → черга wgpu чекає перед шейдером) і read (черга wgpu сигналить після
   шейдера → D3D11 `Wait` перед повторним використанням слота). У wgpu-hal 30 для цього є штатні
   `dx12::Queue::add_wait_fence` / `add_signal_fence` (ставляться перед `queue.submit`). Після копії —
   `Flush` контексту D3D11, інакше D3D12 може чекати сигналу, який ще сидить у черзі D3D11.
5. **Шейдер** `src/nv12.wgsl` — BT.709, обмежений діапазон 16–235, найближча хрома (редакторові потрібна
   білінійна — деталь Фази 8).
6. **Запасний шлях `cpu`** — той самий DXVA-декодер, власна GPU-копія в кільце staging-текстур, `Map`
   через 2 кадри, площини прямо з мапованої пам'яті в `queue.write_texture`. Для порівняння: `mflock` —
   наївний (MF сам блокує текстуру), `sw` — без D3D взагалі (програмний декодер).
7. **Перемотка** — `SetCurrentPosition` (MF стає на ключовий кадр перед ціллю) і декодування вперед до
   потрібного PTS. `--lowlat` = `MF_LOW_LATENCY` на Source Reader (декодер віддає кадр одразу).
8. **Перевірка без еталонного файлу** — генератор (`gen`, Sink Writer, H.264 High, без B-кадрів, GOP як у
   LH) малює в кожному кадрі його номер штрих-кодом (16 біт + інверсія) і 8 кольорових зразків.

## Результати (PLUM-MEDIA: i5-10500, Intel UHD 630 — найслабша ціль; 28.09.2026)

**4K60 H.264 (47 Мбіт/с), шлях без копіювання:**

| вимір | результат | критерій |
|---|---|---|
| швидкість | **113–116 к/с** | ≥ 60 ✓ |
| CPU при рівних 60 к/с | **0,4–0,7 % машини** (4–9 % одного ядра) | ≤ 10 % ✓ |
| правильність | 1200/1200 кадрів з правильним номером, кольори ±1 | — |
| перемотка, GOP 60 (як LH) | медіана 162 мс, макс **261 мс** | ≤ 100 ✗ |
| перемотка, GOP 15 + `--lowlat` | медіана 40 мс, макс **61 мс**, 48/48 точних | ≤ 100 ✓ |

**Запасні шляхи, 4K60:** `cpu` (staging) 50–55 к/с при 2–4 % CPU, кадри правильні — упирається не в
CPU, а в пропускну здатність GPU/пам'яті вбудованої графіки (дві зайві копії 12 МБ через спільну пам'ять:
`Map` чекає на GPU; з `--verify`, коли GPU простоює, Map+upload = 2,2 мс). `mflock` 38 к/с, `sw` 58–66 к/с
при 40–47 % CPU. **1080p60:** zero 505 к/с, cpu 238, mflock 142, sw 263 (43 % CPU).

**Перемотка за GOP (4K, UHD 630):** GOP 60 → макс 261 мс (з lowlat 229); 30 → 140; 15 → 88 (з lowlat 61);
10 → 70. Справжній запис LH 2148×1362@60, GOP 60 — медіана 42, макс 80 мс.

**Якість за GOP** (`quality`, синтетика): PSNR ≥ 46,9 дБ для GOP 60/30/15/10 при однаковому бітрейті —
синтетичний візерунок надто простий, щоб показати ціну частих ключових кадрів; на справжньому екранному
вмісті це треба виміряти в ZK-87 (запис).

## Висновки для плану

- **Шлях без копіювання працює на wgpu 30 без патчів**: `texture_from_raw` + `TextureFormat::NV12` +
  view за площинами + `add_wait_fence`/`add_signal_fence`. Ризик «межі wgpu-hal» знято для Windows.
- **Перемотка ≤ 100 мс на 4K вимагає коротшого GOP у наших записах** (0,25 с = 15 кадрів на 60 к/с) і
  `MF_LOW_LATENCY` у редакторі. LH пише GOP = fps (1 с) — на 4K слабкої графіки це 260 мс. Ціну в бітрейті
  й якості виміряти в ZK-87 на справжньому вмісті; запасний UX — показувати ключовий кадр під час
  перетягування повзунка, точний кадр — на відпусканні.
- **Запасний шлях** годиться як аварійний (кадри правильні, CPU низький), але на 4K вбудованої графіки
  не тримає 60 к/с; у v2 — лише коли імпорт shared handle відмовив.
- **Не перевірено тут:** гібридна пара GPU (на PLUM-MEDIA один адаптер — LUID-зіставлення працює за
  побудовою, але живої перевірки Optimus немає), HEVC/10-біт, NVIDIA/AMD-декодери, вивід у swapchain
  (вимір — у позаекранну текстуру; присвоєння кадру поверхні — один blit).
