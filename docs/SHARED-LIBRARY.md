# Спільна бібліотека: команда / проєкт / модуль (ZK-263, проєкт)

Статус: **закрито рішенням власника 04.10 після прототипу ZK-282 (§9): командного рівня в Google
не робимо** — спільна робота лишається через спільну теку на хмарному диску (рішення 14 у PLAN.md).
Решта документа — як проєктувалось, для історії й на випадок, якщо колись повернемось (повний `drive`
або власний сервер). Етап 3 Google (етап 1 — вхід і «Надіслати в Drive»,
ZK-259/260; етап 2 — синхронізація власної бібліотеки, ZK-162/103). Пов'язане: ZK-162, ZK-103, PLAN.md §5.6.

## 1. Що хочемо

Кілька людей бачать і поповнюють спільні знімки й записи, з правами на трьох рівнях:

- **команда** — усі, хто працює разом (напр. «Plum Dev»);
- **проєкт** — частина команди (напр. «Znimok»);
- **модуль** — частина проєкту (напр. «Запис відео»).

Права успадковуються згори вниз: учасник команди бачить усі її проєкти, якщо проєкт не закритий
окремо. На кожному рівні — чотири дії: **читати**, **додавати**, **редагувати** (позначки, назва, опис),
**видаляти**.

## 2. Головне обмеження — дозволи Google (оцінити до будь-якого коду)

Сьогодні Znimok просить лише `drive.file` (рішення власника 04.10: без чутливих дозволів і без
перевірки застосунку Google). Цей дозвіл дає доступ **лише до файлів, які Znimok створив або які
людина сама відкрила/вибрала в ньому** — і, наскільки відомо з документації, окремо для кожного
користувача. Файл, який колега завантажив зі свого Znimok, для мого Znimok з `drive.file` **не видно
автоматично**, навіть якщо тека спільна.

Звідси три шляхи:

| Варіант | Як | Плюси | Мінуси |
|---|---|---|---|
| **A. Повний `drive`** | Znimok читає спільну теку цілком | Справжня синхронізація, без ручних кроків | Обмежений (restricted) дозвіл → перевірка застосунку Google **і щорічна стороння перевірка безпеки (CASA)** — гроші й тижні щороку; на екрані згоди — «доступ до всіх ваших файлів» |
| **B. `drive.file` + Google Picker** | Людина один раз вибирає спільну теку у вікні Google; нові файли колег — знову через Picker або посилання | Лишаємось без перевірки | **Невідомо**, чи вибір теки дає доступ до її вмісту й нових файлів у ній; якщо ні — для живої команди непридатно. **Перевірити прототипом** (пів дня) до рішення |
| **C. Власний сервер Znimok** | Сервер тримає права й файли (або ключі до них) | Повний контроль над правами | Суперечить принципу «усе на вашому комп'ютері, без телеметрії»; хостинг, безпека, підтримка |

**Рекомендація:** спершу прототип B (одна перевірка: колега кладе файл у теку, вибрану через Picker,
— чи бачить його мій Znimok). Якщо так — B. Якщо ні — рішення власника між A (платна щорічна
перевірка) і відмовою від командного рівня в Google (лишити спільну теку на хмарному диску,
як зараз — рішення 14 у PLAN.md).

## 3. Модель

Права мають **одне джерело правди — дозволи Google Drive**: лише вони справді не пускають сторонніх
до файлів. Власний шар Znimok поверх них показував би права, яких Google не забезпечує, тож його не
робимо; Znimok лише **відображає** рівні на теки Drive і читає з Drive, хто що може.

- команда = **спільний диск** (Shared Drive, Google Workspace) або, для звичайних акаунтів, верхня
  спільна тека;
- проєкт = тека в ньому; модуль = тека в проєкті;
- у теці лежить маленький `znimok-space.json` (назва рівня, тип, uuid, версія формату) — щоб Znimok
  відрізняв свої теки від сторонніх і переживав перейменування;
- ролі Drive → дії Znimok:

| Роль Drive | Читати | Додавати | Редагувати | Видаляти |
|---|---|---|---|---|
| Читач / Коментатор | ✓ | | | |
| Редактор (Writer) | ✓ | ✓ | ✓ | лише своє (у спільних дисках — у кошик) |
| Менеджер вмісту (fileOrganizer) | ✓ | ✓ | ✓ | ✓ |
| Менеджер (organizer) / власник | ✓ | ✓ | ✓ | ✓ + керує учасниками |

**Успадкування:** у Drive дозволи теки переходять на вкладені. Звузити доступ до модуля (закрити від
частини проєкту) Drive дозволяє лише як «обмежений доступ» до теки — **перевірити** на звичайних
акаунтах і в Workspace. Якщо звуження недоступне, модуль може лише **розширювати** коло (додати
людину до модуля, не до всього проєкту).

## 4. Як це бачить людина

- **Бібліотека:** зліва дерево «Моя бібліотека» + команди → проєкти → модулі; бейдж на картці —
  де лежить і чи вже синхронізовано (✓ / ⟳ / ⚠ конфлікт / ☁ лише в хмарі).
- **Фільтри:** за рівнем, за автором, «мої».
- **Поширити → у модуль:** ціль у вікні «Поширити» (поруч з Drive / Jira / Slack), без окремого
  інтерфейсу.
- **Запросити:** з Znimok — e-mail + роль (Znimok викликає Drive `permissions.create`); людина отримує
  звичайний лист Google. **Вийти** — прибрати себе з дозволів; локальні копії лишаються як звичайні
  знімки «Моєї бібліотеки».
- Права, яких немає, видно: кнопки «Редагувати» / «Видалити» неактивні з поясненням «у вас роль
  читача в модулі X».

## 5. Синхронізація, конфлікти, офлайн

Спирається на етап 2 (ZK-162/103), тут — що додає спільність:

- **Ідентичність:** uuid документа в `META` + версія документа (лічильник збережень) + `etag`/ревізія
  Drive. Перейменування не чіпає файл (PLAN §5.6).
- **Зміни:** Drive `changes.list` з токеном сторінки на кожен спільний диск/теку; опитування раз на
  кілька хвилин і при відкритті бібліотеки (push-канали Drive вимагають публічного вебхука — не
  для десктопу).
- **Конфлікт** (двоє змінили ту саму версію): обидва варіанти зберігаються, другий — як
  «Назва (конфлікт, Ім'я, машина)»; нічого не зливається мовчки. Позначки — не зливаємо поблоково
  (поки що).
- **Офлайн:** зміни в черзі на диску (як черга `znimok-share`), повтори з паузами; бейдж ⟳.
- **Видалення з іншої машини:** файл іде в кошик бібліотеки (ZK-55), не зникає; у кошику — хто
  видалив.
- **Великі відео:** завантаження частинами (resumable upload); у бібліотеці колег — мініатюра й
  метадані одразу, сам файл — за потреби (☁).

## 6. Безпека й приватність

- Токени — у сховищі системи (як ZK-259).
- Шифрування на боці клієнта для командних тек — **не** в першій версії: тоді Google не покаже
  попередній перегляд, а ключі доведеться роздавати; повернутися, якщо попросять.
- Знімки можуть містити секрети з екрана: при поширенні в команду — те саме вікно «Поширити» з
  «що приховати» (ZK-279).

## 7. Питання до власника (рішення перед реалізацією)

1. Дозвіл Google: згоден спершу на прототип B (Picker, пів дня)? Якщо B не працює — A (платна
   щорічна перевірка CASA) чи відмова від командного рівня в Google?
2. Чи потрібні звичайні акаунти Google, чи достатньо Google Workspace (спільні диски)? Від цього
   залежить, чи можна звузити доступ до модуля.
3. Чи чіпати запрошення з Znimok (лист від Google), чи лише показувати те, що налаштовано в Drive?
4. Командний рівень — у безкоштовній версії чи з ключем (зачіпає ZK-265)?

## 8. Оцінка після рішень (грубо)

Прототип B — 0,5 дня. Етап 2 (власна синхронізація, ZK-162/103) — передумова, ~1–2 тижні.
Поверх нього: простір/рівні й ролі — 3–4 дні; дерево, бейджі, фільтри — 3 дні; запрошення —
1–2 дні; конфлікти й кошик зі спільних тек — 2–3 дні; самотест на двох акаунтах — 1 день.

## 9. Прототип ZK-282 і рішення (04.10.2026)

Скрипт: `tools/proto/drive_file_sharing.py` (той самий OAuth-клієнт, що й Znimok; лише `drive.file`).
A = власник теки, B = «колега»; тека й файл створені Znimok-ом A, тека поділена з B як writer.

| Хто | Що | Результат |
|---|---|---|
| B | бачить спільну теку (files.get) | **ні** — 404 |
| B | бачить вміст теки (files.list) | **ні** — порожньо |
| B | відкриває файл A за точним id | **ні** — 404 |
| B | додає файл у теку за її id | так |
| A | бачить у своїй теці файл, доданий B | **ні** |
| A | переносить теку в кошик | **ні** — 403 `appNotAuthorizedToChild` (у теці «чужий» для застосунку файл) |

Висновок: доступ `drive.file` — **окремо для кожної людини**: файл, створений Znimok-ом одного
акаунта, для Znimok-а іншого акаунта не існує, навіть у спільній теці й навіть за точним id. Не
працює ні спільна бібліотека, ні «скринька», куди всі складають знімки для одного власника.
Вибір теки у вікні Google Picker, за свідченнями розробників, доступу до її вмісту теж не дає
(перевіряти окремо не стали — рішення від цього не змінюється).

**Рішення власника** (питання §7): 1) прототип — так; якщо не працює — **без командного рівня в
Google** (не повний `drive` з щорічною перевіркою CASA і не власний сервер); 2) акаунти — звичайні й
Workspace; 3) запрошення — з Znimok; 4) безкоштовно чи з ключем — разом із ZK-265. Пункти 2–3
актуальні лише якщо до командного рівня колись повернемось.
