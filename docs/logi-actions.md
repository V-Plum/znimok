# Logi Options+ integration (ZK-118) — research notes

What the Logi Actions SDK is, how a Znimok plugin would fit, and what it needs. Written
01.10.2026 from the SDK docs (`https://logitech.github.io/actions-sdk-docs/`, machine-readable copy
kept at `C:\AIHome\builds\logi-sdk\llms-full.txt`) and three open-source plugins
(HapticWebPlugin, ReaperHaptic, logi-now-playing). Nothing here is built yet.

## How the ecosystem works

- **Logi Plugin Service (LPS)** ships with Logi Options+ (and Loupedeck). It loads plugins, routes
  device events to them and draws their buttons. Plugins live in the user's profile:
  `%LOCALAPPDATA%\Logi\LogiPluginService\Plugins` /
  `~/Library/Application Support/Logi/LogiPluginService/Plugins`. No administrator rights.
- **Two SDKs.** C#: a .NET 8 class library loaded *in-process* by LPS, referencing
  `PluginApi.dll` from the LPS install (`C:\Program Files\Logi\LogiPluginService\` or
  `/Applications/Utilities/LogiPluginService.app/Contents/MonoBundle/`); the full feature set.
  Node.js (beta, Plugin API 6.2.3 / Options+ 1.97; macOS since API 6.3 / Options+ 2.2): a separate
  Node process over IPC; a limited, growing feature set — **its API has no plugin events, so no
  haptics**. → Znimok's plugin is C#.
- **Actions.** `PluginDynamicCommand` (a button: `RunCommand`), `PluginDynamicAdjustment` (a dial:
  `ApplyAdjustment(diff)`, press = reset, `GetAdjustmentValue` shown by the dial),
  `PluginDynamicFolder` (a "control center" page the plugin fills, with `GetNavigationArea`),
  `ActionEditorCommand` (a command with user-set parameters), multistate actions. Group names
  nest with `###` (3 levels). Button pictures: `GetCommandImage` (PNG 80×80 or SVG;
  `BitmapBuilder` draws text over a background) or files in `actionicons/` by naming convention;
  `ActionImageChanged()` redraws.
- **Where the actions show.** Options+ → the device's customization → "All Actions → Installed
  Plugins". Assignable to the MX Creative Keypad (LCD buttons), Dialpad (dial, roller, buttons)
  and the **Actions Ring** — the on-screen 8-button overlay that any MX device opens (the mouse's
  gesture/thumb button); folders inside the Ring too. Whether a plugin command can go straight on
  an MX Master 4 side button (without the Ring) — *check in Options+ with the mouse*.
- **Application plugin vs universal.** `ClientApplication.GetProcessName()` = `znimok-app`
  (`GetBundleName()` = `ua.plum.znimok.app` on macOS) makes the plugin an *application plugin*:
  with "Adapt to App" on, the device switches to the Znimok profile when Znimok is in front.
  `HasNoApplication = true` + `UsesApplicationApiOnly = true` makes a universal one, available in
  every profile (HapticWeb does that). Znimok wants both halves: an application plugin for the
  editor's tools, but "New screenshot" / "Record" must work from any app → *universal plugin with
  `GetProcessName` set* (verify that the combination gives the Ring the actions everywhere while
  "Adapt to App" still picks the Znimok profile; the SDK allows `IsProcessNameSupported` too).
- **Default profiles** `profiles/DefaultProfile70.lp5` (Keypad), `71` (Dialpad), `72` (Actions
  Ring) — exported from Options+ after laying the buttons out by hand; applied on first install.
- **Localization**: XLIFF per language (`localization/<Plugin>_uk-UA.xliff`), generated by
  `logiplugintool xliff`; the plugin may follow the host app's language
  (`Localization.SetCurrentLanguage`).

## Haptics (MX Master 4)

Plugin API 6.2.1 / Options+ 1.95. The MX Master 4 is the only haptic device.

- The plugin declares **events** — in code (`PluginEvents.AddEvent(name, displayName,
  description)`) or in `events/DefaultEventSource.yaml` — and raises them
  (`PluginEvents.RaiseEvent(name)`). `events/extra/eventMapping.yaml` maps each event to a
  waveform (`DEFAULT` plus per-device overrides); `LoupedeckPackage.yaml` needs
  `pluginCapabilities: [HasHapticMapping]`. The user can re-map waveforms in Options+.
- 15 waveforms: `sharp_state_change`, `damp_state_change`, `sharp_collision`, `damp_collision`,
  `subtle_collision`, `happy_alert`, `angry_alert`, `completed`, `square`, `wave`, `firework`,
  `mad`, `knock`, `jingle`, `ringing`. Logitech's guidance: subtle ones for frequent events
  (snapping, hover), intense ones for notifications; debounce (ReaperHaptic uses 80–1000 ms).
- There is no haptics API outside a plugin: no HID, no CLI. Everything goes through LPS.

Draft event source for Znimok (names are stable identifiers; the user sees the display names):

| event | when | DEFAULT waveform |
|---|---|---|
| `shotTaken` | a screenshot saved (hotkey, overlay, "record this window" start) | `sharp_state_change` |
| `copied` | copied to the clipboard | `subtle_collision` |
| `recordStart` / `recordStop` | recording started / stopped | `sharp_state_change` / `completed` |
| `recordPause` / `recordResume` | paused / resumed | `damp_state_change` |
| `exportDone` | export / save-as finished | `completed` |
| `textRead` / `codesRead` | OCR / codes done | `happy_alert` |
| `failed` | a capture, recording or export failed | `angry_alert` |
| `snap` | a mark snapped to a guide while dragging (the editor has no snapping yet — later) | `subtle_collision` |

## How the plugin talks to Znimok

The plugin is just another client of the app's command layer, like the CLI and MCP (PLAN §5.4):
the app's IPC server (`znimok-ipc`: JSON-RPC over a user-only named pipe / unix socket, `hello`
with the session token from `ipc-token`). LPS runs in the user's session, so the plugin can read
the token and connect directly (a small C# client: `NamedPipeClientStream` /
`UnixDomainSocketEndPoint`, line-delimited JSON). Alternative that needs no client code: spawn
`znimok.exe <cmd>` per action — slower (~100 ms a start), fine for a first prototype.

Two directions:

1. **Device → Znimok (commands).** New IPC methods the app answers, backed by what the hotkeys and
   the tray already do (`hotkeys::Action`, `rec::toggle/stop/toggle_pause`, `App::undo/redo/
   set_tool/zoom_*`):
   `capture.start {mode: region|screen|clipboard|editor|codes|text}`, `record.toggle`,
   `record.pause`, `record.stop`, `editor.undo`, `editor.redo`, `editor.tool {name}`,
   `editor.zoom {step|fit|100}`, `video.scrub {frames}`, `app.state` →
   `{page: library|editor|overlay|recording, tool, zoom, can_undo…}` (for button pictures and
   the Ring's context). All of them run on the UI thread like the devtools requests
   (`devlog::poll` pattern: queue in the hub, drained a few times a second).
2. **Znimok → device (events for haptics and button states).** A long poll like
   `devtools.wait`: `app.wait {since}` → `{events: [{name, t}], state}`; the plugin keeps one
   connection waiting and raises the haptic event / repaints buttons when something comes. Znimok
   emits into the hub from the places where the toast / tray state changes today.

Neither side needs admin rights, certificates or network ports.

## Distribution

- Package: `logiplugintool pack ./bin/Release ./Znimok_1_0.lplug4` (a zip with
  `metadata/LoupedeckPackage.yaml`, `metadata/Icon256x256.png`, `win/`, `mac/`, `actionicons/`,
  `events/`, `profiles/`, `localization/`); `logiplugintool verify` checks it. Installs by
  double-click or `LoupedeckPluginPackageInstaller`; during development a `.link` file in the
  Plugins folder points at the build output, `loupedeck://plugin/Znimok/reload` reloads.
- The same DLL serves Windows and macOS (`pluginFolderWin` / `pluginFolderMac`); managed code
  loaded by LPS — no notarization of our own, nothing changes with the Apple certificate.
- **Logi Marketplace**: submission form `https://marketplace.logitech.com/contribute`, manual
  review, "reach out after ten working days"; needs the Marketplace Developer Agreement, our own
  EULA, a privacy policy (we have `docs/privacy*.md`), valid links, no GPL code (MIT/Apache only
  for OSS parts; our own proprietary licence is fine). Until then: the `.lplug4` in the GitHub
  release, installed by double-click.
- Separate repository (`V-Plum/znimok-logi`): .NET project, GitHub Actions builds the `.lplug4`
  on Windows (the DLL is platform-neutral), tests against a stub IPC server.

## What is needed before the first prototype

1. **Building needs no Options+.** `PluginApi.dll` ships inside the `LogiPluginTool` .NET global
   tool (`~/.dotnet/tools/.store/**/PluginApi.dll`) — HapticWebPlugin's CI builds on
   `windows-latest` from just the .NET 8 SDK and that tool, logi-now-playing's on macOS. So the
   plugin builds on PLUM-MEDIA and in GitHub Actions; only *running* it needs LPS.
2. **Where it runs (01.10.2026):** the MX Master 4 and Options+ are on PLUM-PC (the owner's work
   machine); an MX Creative Keypad is at a friend's, who can install a ready `.lplug4` by
   double-click for simple tests (no development there). Testing loop: build here → `.lplug4` →
   the owner installs it on PLUM-PC (Options+ ≥ 1.95 for haptics) with Znimok installed there
   too → feedback. The Keypad's layout (`DefaultProfile70.lp5`) is tried last, by the friend.
3. **The command layer in Znimok** (one Znimok ticket, ~1 day): the IPC methods above and the
   event hub — useful for the CLI and MCP as well.
4. **Icons** in the design system's style, 80×80 PNG / SVG, for ~12 actions.
5. **Marketplace**: the owner signs the Developer Agreement and files the submission (an account
   on marketplace.logitech.com); EULA text.
